# r5ctrlr
C and HDL code for a controller which integrates programmable logic (Xilinx Zynq Ultrascale+ FPGA PL), realtime processor (baremetal R5) and linux (on A53). 

Two FPGA cards are supported:
- [Xilinx ZCU102](https://www.amd.com/en/products/adaptive-socs-and-fpgas/evaluation-boards/ek-u1-zcu102-g.html)
- [Enclustra Mercury+ XU1 (ME-XU1-6EG-1I-D11E)](https://www.enclustra.com/en/products/system-on-chip-modules/mercury-xu1/) with [ST1 baseboard](https://www.enclustra.com/en/products/base-boards/mercury-st1/).

# Installation procedure
All the steps needed to setup projects for vivado, vitis and yocto, starting from the files found in this repository are now described.

<!-- TOC --><a name="directory-structure"></a>
## Directory structure
Make a base directory for your project in your local filesystem where it is convenient for you; in this directory we will later create this subdirectories (instructions provided in following sections):
- `gitcode` : local mirror of this git repo
- `sdk-linux` : all the libraries needed to cross-compile applications for A53/linux on the FPGA; it is generated by yocto; it cannot be simply moved to another location, as it contains absolute paths: in case, just reinstall it
- `vitis-workspace` : environment to cross-compile applications for A53/linux and R5/baremetal on the FPGA; it contains the "platform", some config files and the structures for the A53/linux and R5/baremetal apps; the actual code is in `gitcode/c`, along with makefiles to do the compilation without vitis; anyway, vitis is useful to download both A53 and R5 apps to the target zynq and debug them.
This directory can be moved to any location, but the source reference to the git-mirrored directory must be updated.
- `vivado-prj` ; it contains the subdirectories:
  * `zcu102` : base directory for the Vivado design of the PL (programmable logic part of FPGA) for the Xilinx ZCU102 board. This directory can be moved to any location, but the relative location of the IP sources (`gitcode/hdl`) and `ip_repo` repository folder must be updated.
  * `enclustra-xu1st1` : base directory for the Vivado design of the PL (programmable logic part of FPGA) for the Enclustra Mercury+ XU1 board with ST1 baseboard. This directory can be moved to any location, but the relative location of the IP sources (`gitcode/hdl`) and `ip_repo` repository folder must be updated.
  * `ip_repo` : repository folder, which is common for all the boards
- `yocto-prj` : base directory to compile linux image with boot binaries, kernel and rootfs. This directory cannot be be moved to other locations, as it contains absolute paths; if you want to move it, you must start a new yocto project with repo init etc.

<!-- TOC --><a name="clone-git-directory"></a>
## Clone git directory
When you clone a remote git repo to your local directory, it takes the name of the repo; we will then rename it to "gitcode" for clarity:
```
cd <base dir>
git clone git@github.com:valerixb/r5ctrlr.git
mv r5ctrlr gitcode
```

<!-- TOC --><a name="setup-vivado-project"></a>
## Setup Vivado project
This git repo includes a backup of the Vivado projects for the FPGA PL and PS for all the supported FPGA cards in directory `vivado_prj_backup`; the board-specific subdirectories are:
* `zcu102`
* `enclustra-xu1st1`

In attidion, there is a common `ip_repo` folder, used by all the boards.

Each board-specific subdirectory contains a tcl script that recreates the project, using the other backup files stored in the same subdirectory.
To re-create the Vivado project for each of the supported boards, in your base directory make a new subfolder called `vivado-prj` and copy there the content of `gitcode/vivado_prj_backup`. 
Then, for every board-specific subdirectory, cd to the subdirectory, run Vivado, but don't open any project; instead, in the TCL command line run the command:
```
source ./r5ctrlr.tcl
```
This reconstructs all the project. Save and exit Vivado. In your board-specific directory, Vivado created a `r5ctrlr` subdirectory; move all its content into the parent dir (i.e. the board-specific directory), saying YES when prompted to merge directories and overwrite files. Then remove the now empty `r5ctrlr` directory. Open Vivado again and build the bitfile.

Note that Vivado project directory can be moved, as it does not contain absolute paths, but the links to hdl files in the block design and the `ip_repo` path in vivado settings must be updated. 
Also the `ip_repo` repository folder can be moved, but the links to hdl files in the IPs must be updated.


<!-- TOC --><a name="setup-yocto"></a>
## Setup yocto
<!-- TOC --><a name="init-repo-using-xilinx-edf-manifest"></a>
### Init repo using xilinx edf manifest
Start a local yocto project using Xilinx EDF as a base (note the manifest selection by option "-m"); put everything on a new branch called "r5ctrlr_devel".
```
cd <base dir>
mkdir -p yocto-prj
cd yocto-prj
repo init -u https://github.com/Xilinx/yocto-manifests.git -b rel-v2025.2 -m default-edf.xml
repo sync
repo start r5ctrlr_devel --all
source edf-init-build-env
```
Note that the script performs an automatic `cd ./build`, so your shell is now in build subdirectory. From now on it is assumed that the `edf-init-build-env` has been sourced.


<!-- TOC --><a name="import-custom-distro-configuration"></a>
### Import custom distro configuration
All the yocto customizations for MaxIV and r5ctrlr project in particular are defined in a custom distro called "maxiv".
Just copy (merge) the content of the directory `<base dir>/gitcode/yocto` into `<base dir>/yocto-prj`. It's mainly a simple customization of `<base dir>/build/conf` files plus the addition of a new `meta-user` layer that does all the work. Note that this layer also includes the SCPI server, R5 executable and web pages. Some useful shell scripts are also added to the build directory to automate common yocto procedures (build, configure, make a SD card from the image).
Finally, a `meta-vivadoprj` layer is also added, which is were info about the Vivado PL and PS project will be passed to yocto.


<!-- TOC --><a name="export-vivado-project-into-a-system-device-tree"></a>
### Export Vivado project into a System Device Tree
Go into each of the board-specific directory of the vivado project, namely:
* `<base dir>/vivado-prj/zcu102`
* `<base dir>/vivado-prj/enclustra-xu1st1`

In each of the board-specific directories open vivado, load the r5ctrlr project and export the hardware as a .xsa file (include bitstream, but do not include binary, which is the format used for dynamic PL reconfig); accept the default name for the xsa. Close vivado.

Then, still in the board-specific directory, we have to generate a "system device tree" ("SDT") from the .xsa file exported by Vivado; we will generate the SDT into a `output_sdt` subdirectory. The commands are different for the different boards.

<!-- TOC --><a name="sdt-for-zcu102"></a>
#### SDT for ZCU102
```
cd <base dir>/vivado-prj/zcu102
sdtgen -xsa design_1_wrapper.xsa \
       -dir output_sdt \
       -board_dts zcu102-rev1.0
```

<!-- TOC --><a name="sdt-for-enclustra-xu1+st1"></a>
#### SDT for Enclustra XU1+ST1
```
cd <base dir>/vivado-prj/enclustra-xu1st1
sdtgen -xsa Mercury_XU1_ST1.xsa \
       -dir output_sdt \
       -user_dts "../../yocto-prj/sources/meta-user/recipes-bsp/device-tree/files/xu1st1/enclustra_xu1st1.dtsi"
```
A warning is generated, but it can be safely ignored:
```
WARNING: CONFIG.PSU__PSS_REF_CLK__FREQMHZ not found. Using default value for XPAR_PSU_PSS_REF_CLK_FREQ_HZ.
```

<!-- TOC --><a name="import-vivado-project-into-a-layer"></a>
### Import Vivado project into a Yocto Layer
The previously generated SDT (=vivado design) is now imported into yocto `meta-vivadoprj` layer invoking the command `gen-machine-conf`; this must be done for all the supported boards; the commands are different and detailed in next sections. Info about all the boards is stored in the layer; the right one will be selected by Yocto at build time, depending on the `MACHINE` used in the build command. This is what yocto calls a "multiconfig": it's meant for this very purpose, i.e. same project on different hardware.


<!-- TOC --><a name="sdt-import-commands-for-zcu102"></a>
#### SDT import commands for ZCU102
```
cd <base dir>/yocto-prj
source edf-init-build-env
```
(note: now we are in `build` subdir)
```
MACHINE=qemuarm64 gen-machine-conf parse-sdt \
    --hw-description ../../vivado-prj/zcu102/output_sdt \
    -c ../sources/meta-vivadoprj/conf \
    --add-config CONFIG_YOCTO_BBMC_CORTEXR5_0_BAREMETAL=y \
    --machine-name r5ctrlr-zcu102
```


<!-- TOC --><a name="sdt-import-commands-for-enclustra-xu1+st1"></a>
#### SDT import commands for Enclustra XU1+ST1
```
cd <base dir>/yocto-prj
source edf-init-build-env
```
(note: now we are in `build` subdir)
```
MACHINE=qemuarm64 gen-machine-conf parse-sdt \
    --hw-description ../../vivado-prj/enclustra-xu1st1/output_sdt \
    -c ../sources/meta-vivadoprj/conf \
    --add-config CONFIG_YOCTO_BBMC_CORTEXR5_0_BAREMETAL=y \
    --machine-name r5ctrlr-xu1st1
```


<!-- TOC --><a name="build-linux-image"></a>
### Build linux image
As always, start initializing the yocto environment:
```
cd <base dir>/yocto-prj
source edf-init-build-env
```
Then a script (provided by this repo) can be used to build the image; it depends on the board used.

For ZCU102 use:
```
./zcu102-build
```
For Enclustra XU1+ST1 use:
```
./xu1st1-build
```

The script performs all the necessary steps to make clean and build an image with bootbin, kernel and rootFS. It includes the R5 executable and the SCPI server. The final image is saved into `build/saved_images/<FPGA_board_name>`.



<!-- TOC --><a name="make-an-sd-card-from-the-compiled-image"></a>
### Make an SD card from the compiled image
Insert a SD card with size of 32 GB minimum; in the script it is assumed that it is seen as `/dev/sde` (change it if it's different on your computer); then, as always, initialize the yocto environment:
```
cd <base dir>/yocto-prj
source edf-init-build-env
```

Then a script (provided by this repo) can be used to write the image to the SD card; it depends on the board used.

For ZCU102 use:
```
./zcu102-makeSD
```
For Enclustra XU1+ST1 use:
```
./xu1st1-makeSD
```

The script will partition the SD and copy all the necessary files (it takes some time). Then eject the SD card and put it into the FPGA board. You are now ready to boot.

<!-- TOC --><a name="serial-ttys"></a>
#### Serial TTYs
The configuration of the serial TTYs depends on the FPGA board. Details in the following sections.


<!-- TOC --><a name="serial-ttys-for-zcu102"></a>
#### Serial TTYs for ZCU102
Linux uses UART0 and R5 uses UART1 as serial consoles; they are both accessible from a single micro-USB connector on ZCU102 (along with other two serial ports in which we are not interested here).


<!-- TOC --><a name="serial-ttys-for-enclustra-xu1+st1"></a>
#### Serial TTYs for Enclustra XU1+ST1
Linux uses UART0 on the ST1 micro USB connector, once the onboard FTDI chip has been properly configured using Enclustra MCT utility; for more details see [Enclustra XU1+ST1 reference design instructions](https://github.com/enclustra/Mercury_XU1_ST1_Reference_Design/blob/master/doc/Mercury_XU1_ST1.pdf).
On the other hand, the R5 processor uses UART1, which has been connected in Vivado to PS MIO 40 and 41, which are routed on IO4 connector (pin 1 and 3) on ST1 baseboard; please note that IO levels are 1.8V even if the IO4 connector provides a 3.3V rail. A suitable serial to USB converter can be used to connect to a PC, for example FTDI cable with P/N "TTL-232RG-VREG1V8-WE"; it must be connected in null modem configuration:

* PS UART1 TXD = MIO 40 = ST1 IO4 connector pin 1 (1.8V even if the connector has a 3.3V supply pin) = FTDI RX
* PS UART1 RXD = MIO 41 = ST1 IO4 connector pin 3 (1.8V even if the connector has a 3.3V supply pin) = FTDI TX
* GND = ST1 IO4 connector pin 9 = FTDI GND

In the build directory another shell script is supplied; it's called `zcu102-u-boot-config` for the ZCU102 board and `xu1st1-u-boot-config` for Enclustra XU1+ST1; it does the menuconfig for bootbin and, after you close the GUI, it saves the temporary configuration file to a safe position in the meta-user layer (very important!).

<!-- TOC --><a name="script-for-additional-kernel-configuration"></a>
### Script for additional kernel configuration
In the build directory another shell script is supplied; it's called `zcu102-kernel-config` for the ZCU102 board and `xu1st1-kernel-config` for Enclustra XU1+ST1; it does the menuconfig for the kernel and, after you close the GUI, it saves the temporary configuration file to a safe position in the meta-user layer (very important!).


<!-- TOC --><a name="use-yocto-to-build-the-linux-sdk"></a>
## Use yocto to build the linux SDK
In the build directory there is a script that lets you build the SDK for linux, i.e. all the libraries that are needed to cross compile an application for A53/linux. The script is called `r5ctrlr-sdk` and it does not depend on the particular FPGA board used. It takes a while to compile; once it completes, the SDK must be installed to a specific directory; it cannot be moved because it contains absolute paths. The installation script is generated by the build process and can be found here:
```
./build/tmp/deploy/sdk/maxiv-glibc-x86_64-meta-edf-app-sdk-cortexa72-cortexa53-amd-cortexa53-common-toolchain-v2025.2.sh
```
When you run this shell script, it asks you for the installation directory; in our case use this:
```
<base dir>/sdk-linux
```
Note that the SDK is for A53/linux only; the libraries necessary to cross compile applications for baremetal R5 are generated by Vitis in the "platform".


<!-- TOC --><a name="setup-vitis"></a>
## Setup Vitis
To cross compile applications for A53/linux and R5/baremetal it is possible to follow to ways:
- Vitis environment
- standard workflow from command line with the provided makefiles

As editor it's convenient to use visual studio code in both cases.
Vitis debugger is a useful tool, as it can download, run and debug the applications (with step execution, breakpoints and all that) for both processors.

The application executables for A53/linux and R5/baremetal are common among different boards, as the PL was developed with the same address map.

In Vitis these items need to be setup:
- a platform for the FPGA board (any of the supported ones) with the custom PL design made in Vivado
- an R5/baremetal app = control loop
- an A53/linux app = SCPI server

> [!NOTE]
>
> Even if some users may prefer the traditional makefile workflow, Vitis must be used once to generate the platform, which provides the libraries necessary to build R5 baremetal applications; for A53 linux, the libraries were compiled by yocto into the SDK, as outlined in previous section.

Start making a directory called:
```
<base dir>/vitis-workspace
```
cd there, run: ```vitis&``` and choose the previous directory as workspace. Click OK if it complains about "file watch errors": it's not a real problem.

First, we need to make a new "platform"; copy the `.xsa` from one of the board-specific subdirectories of `vivado-prj` to `vitis-workspace` directory, so they are separated and one can work on vivado while using an old, stable xsa for vitis. As said earlier, any of the board .xsa can be used for cross-compilation, as the executables are common to all FPGA boards.
In Vitis use the menu command:
```
file/new component/platform
```
Call the platform "r5ctrlr_platform"; it's important to use the right platform and domain names, as they are referenced in the makefiles for the standalone compilation flow.

Start adding a R5#0/baremetal domain called "R5_0_baremetal"; add to it `libmetal` and `openamp`. 
In the R5 BSP, assign UART1 as stdin/stout, instead of the default UART0. In addition, set the timer to `PL_r5_sleep_timer_0` instead of the default (which is used as sampling timer instead).

Regenerate the BSP

Then add an A53/linux domain called "A53_linux".

Now it's time to compile the platform.

Then create R5app and A53app starting from the "empty application" example: select menu command:
```
File/New Example
```
Then go to the list that appears in the left pane and select `Empty Application` for R5 and `Linux Empty Application` for A53. Call the R5/baremetal application `R5app` and the A53/linux one `A53app`.

> [!NOTE]
>
> If one starts from a new application using menu command `File/New Component/Application` instead of starting from an example empty application, important environment configuration are missed and the application won't compile.

For the A53 select the sysroot previously generated by yocto:
```
<base dir>/sdk-linux/sysroots/cortexa72-cortexa53-xilinx-linux
```

> [!TIP]
>
> Now, before proceeding, it's useful to make a backup copy of `<base dir>/vitis-workspace/_ide/.peers.ini`, in case it gets corrupted by a vitis crash; one can call it `.peers.ini.backup`.


Start with no source files (delete the sample .c and .h generated by vitis, if any); then close vitis, open a terminal and make a link in vitis `src` directory to the appropriate subfolders of the git-mirrored directory:
```
cd <base dir>/vitis-workspace/R5app/src
ln -s ../../../gitcode/c/r5 r5src
ln -s ../../../gitcode/c/common commonsrc

cd <base dir>/vitis-workspace/A53app/src
ln -s ../../../gitcode/c/a53 a53src
ln -s ../../../gitcode/c/common commonsrc
```

Then open Vitis again.

In r5app, open `settings/UserConfig.cmake` and:
- add the math library (`-lm` compiler directive)
- tell the compiler where to find the linker file, which is in the git-mirrored directory structure (it's file `<base dir>/gitcode/c/r5/lscript.ld`)
- add the git-mirrored directories as include directories (`-I` directive)
- add the sources to be compiled:
  ```
  commonsrc/rsc_table.c
  commonsrc/rproc.c
  commonsrc/platform.c
  commonsrc/sample_shmem.c
  r5src/r5_main.c
  r5src/cn0585_gpio.c
  r5src/cn0585_dac.c
  r5src/cn0585_adc.c
  r5src/doubledsplib.c
  ```
- `-O0`
- `-g3`


In A53/linux app, open `settings/UserConfig.cmake` and:
- add `-lm -lmetal -lopen_amp` linker directives
- add the git-mirrored directories (A53 and common) as include directories (`-I` directive); in the GUI you can put "src/a53src" and "src/commonsrc", as the "browse" link ends up putting an unnecessary absolute path
- add the sources to be compiled:
  ```
  src/commonsrc/rsc_table.c
  src/commonsrc/rproc.c
  src/commonsrc/platform.c
  src/commonsrc/sample_shmem.c
  src/a53src/linux_main.c
  src/a53src/SCPIserver.c
  ```
- `-O0`
- `-g3`

After compilation, the elf executables must be copied to the yocto structure to be included in the image; the locations are:
```
<base dir>/yocto-prj/sources/meta-user/recipes-apps/r5ctrlr-r5app/files/R5app.elf
<base dir>/yocto-prj/sources/meta-user/recipes-apps/r5ctrlr-scpi-serv/files/r5ctrlr-scpi-serv
```
Note that the A53 app has been renamed to `r5ctrlr-scpi-serv` (without the .elf extension); it is automatically run by linux at boot. The R5 executable is also automatically run at boot by u-boot.


<!-- TOC --><a name="compilation-without-vitis"></a>
### Compilation without vitis
It is possible to compile both the SCPI server for A53/linux and the control loop for R5/baremetal without Vitis: Makefiles are provided for this. Note that the makefile for linux automatically runs the environment setup (`. <base dir>/sdk-linux/environment-setup-cortexa72-cortexa53-amd-linux`) for the linux SDK previously compiled by yocto, so one does not need to do that manually.
Anyway, Vitis must be used at least once to build the "platform", i.e. the standard libraries for R5/baremetal; as said, the standard libraries for A53/linux are compiled by yocto.
