# Installation procedure
All the steps needed to setup projects for vivado, vitis and yocto, starting from the files found in this repository are now described.

<!-- TOC --><a name="directory-structure"></a>
## Directory structure
Make a base directory for your project in your local filesystem where it is convenient for you; in this directory we will create this subdirectories:
- `gitcode` : local mirror of this git repo
- `sdk-linux` : all the libraries needed to cross-compile applications for A53/linux on the FPGA; it is generated by yocto; it cannot be simply moved to another location, as it contains absolute paths: in case, just reinstall it
- `vitis-workspace` : environment to cross-compile applications for A53/linux and R5/baremetal on the FPGA; it contains the "platform", some config files and the structures for the A53/linux and R5/baremetal apps; the actual code is in gitcode/c, along with makefiles to do the compilation without vitis; anyway, vitis is useful to download both A53 and R5 apps to the target zynq and debug them.
This directory can be moved to any location, but the source reference to the git-mirrored directory must be updated.
- `vivado-prj` : base directory for the Vivado design of the PL (programmable logic part of FPGA). This directory can be moved to any location, but the relative location of the IP sources (gitcode/hdl) must be updated.
- `yocto-prj` : base directory to compile linux image with boot binaries, kernel and rootfs. This directory cannot be be moved to other locations, as it contains absolute paths; if you want to move it, you must start a new yocto project with repo init etc.

<!-- TOC --><a name="clone-git-directory"></a>
## Clone git directory
When you clone a remote git repo to your local directory, it takes the name of the repo; we will then rename it to "gitcode" for clarity:
```
cd <base dir>
git clone git@github.com:valerixb/r5ctrlr.git
mv r5ctrlr gitcode
```

<!-- TOC --><a name="setup-vivado-project"></a>
## Setup Vivado project
In this git repo there is a backup of the Vivado project for the FPGA PL in directory `vivado_prj_backup`; it contains a tcl script that recreates the project. The script itself provides useful info in the comments and in the "print_help" method. Anyway, one can just open Vivado from a convenient directory and run the script from vivado tcl command line. Note that Vivado project directory can be moved, as it does not contain absolute paths (but check the links to hdl files that you put in the IPs).


<!-- TOC --><a name="setup-yocto"></a>
## Setup yocto
<!-- TOC --><a name="init-repo-using-xilinx-edf-manifest"></a>
### Init repo using xilinx edf manifest
Instructions to start a local yocto project using Xilinx EDF as a base (note the manifest selection by option "-m"); I put everything on a new branch called "r5ctrlr_devel".
```
cd <base dir>
mkdir -p yocto-prj
cd yocto-prj
repo init -u https://github.com/Xilinx/yocto-manifests.git -b rel-v2025.2 -m default-edf.xml
repo sync
repo start r5ctrlr_devel --all
source edf-init-build-env
```
Note that the script performs an automatic `cd ./build`, so your shell is now in build subdirectory. From now on it is assumed that the `edf-init-build-env` has been sourced.

<!-- TOC --><a name="import-vivado-project"></a>
### Import Vivado project
Export .xsa from vivado (include bitstream, but do not include binary, which is the format used for dynamic PL reconfig)
Generate system device tree:
```
cd <base dir>/vivado-prj
sdtgen -xsa design_1_wrapper.xsa -dir output_sdt -board_dts zcu102-rev1.0
cd <base dir>/yocto-prj
source edf-init-build-env
```
(note: now we are in `build` subdir)
```
bitbake-layers create-layer ../sources/meta-vivadoprj
bitbake-layers add-layer ../sources/meta-vivadoprj
```
Remove the auto generated `sources/meta-vivadoprj/recipes-example` directory, as we won't use that.

In `<base dir>/conf/local.conf`, uncomment the line:
```
MACHINE ??= "qemuarm64"
```
Now we import the SDT (=vivado design) into yocto invoking `gen-machine-conf` :
```
gen-machine-conf parse-sdt --hw-description ../../vivado-prj/output_sdt -c ../sources/meta-vivadoprj/conf -l ./conf/local.conf --add-config CONFIG_YOCTO_BBMC_CORTEXR5_0_BAREMETAL=y --machine-name custom-machine
```
Note: some xilinx documentation seems to suggest to use `MACHINE=zynqmp-zcu102-sdt-full`, but that's wrong because it's an example xilinx machine! You must use ANOTHER one, with your own name; make it up; I use "custom-machine"; if you use that particular name, xilinx recognizes it, overrides your configuration, builds its own example and you loose your mind trying to figure out what's going on.

It takes forever, but at the end the configuration is written into `sources/meta-vivadoprj`. It also adds the correct `MACHINE` into `build/conf/local.conf`, along with other lines:
```
MACHINE = "custom-machine"
# Avoid errors in some baremetal configs as these layers may be present
# but are not used.  Note the following lines are optional and can be
# safetly disabled.
SKIP_META_VIRT_SANITY_CHECK = "1"
SKIP_META_SECURITY_SANITY_CHECK = "1"
SKIP_META_TPM_SANITY_CHECK = "1"
```
Remove all of them (including the one that defines the `MACHINE`), as they will be defined in our distro configuration in next section.

<!-- TOC --><a name="import-custom-distro-configuration"></a>
### Import custom distro configuration
All the yocto customizations for MaxIV and r5ctrlr project in particular are defined in a custom distro called "maxiv'.
Just copy (merge) the content of the directory `<base dir>/gitcode/yocto` into `<base dir>/yocto-prj`. It's mainly a simple customization of `<base dir>/build/conf` files plus the addition of a `new meta-user` layer that does all the work. Note that this layer also includes the SCPI server, R5 executable and web pages. It also installs some useful shell scripts to automate common yocto procedures (build, configure, make a SD card from the image).

<!-- TOC --><a name="build-linux-image"></a>
### Build linux image
As always, start initializing the yocto environment:
```
cd <base dir>/yocto-prj
source edf-init-build-env
```
Then run the shell script:
```
./yoctix-build
```
It performs all the necessary steps to make clean and build an image with bootbin, kernel and rootFS. It includes the R5 executable.

<!-- TOC --><a name="make-an-sd-card-from-the-compiled-image"></a>
### Make an SD card from the compiled image
Insert a SD card with size of 32 GB minimum; in the script it is assumed that it is seen as `/dev/sdb` (change it if it's different on your computer); then, as always, initialize the yocto environment:
```
cd <base dir>/yocto-prj
source edf-init-build-env
```
then run the shell script:
```
./yoctix-makeSD
```
This will partition the SD and copy all the necessary files (it takes some time). Then eject the SD card and put it into the Zynq. You are now ready to boot. Note that linux uses UART0 and R5 uses UART1; they are both accessible from a single micro-USB connector on ZCU102 (along with other two serial ports in which we are not interested here).


<!-- TOC --><a name="script-for-additional-boot-configuration"></a>
### Script for additional boot configuration
In the build directory another shell script is supplied; it's called `yoctix-u-boot-config`; it does the menuconfig for bootbin and -very important!- after you close the GUI it saves the temporary configuration file to a safe position in the meta-user layer.

<!-- TOC --><a name="script-for-additional-kernel-configuration"></a>
### Script for additional kernel configuration
In the build directory another shell script is supplied; it's called `yoctix-kernel-config`; it does the menuconfig for the kernel and -very important!- after you close the GUI it saves the temporary configuration file to a safe position in the meta-user layer.


<!-- TOC --><a name="use-yocto-to-build-the-linux-sdk"></a>
## Use yocto to build the linux SDK
In the build directory there is a script that lets you build the SDK for linux, i.e. all the libraries that are needed to cross compile an application for A53/linux. The script is called `yoctix-sdk`; it takes a while to compile; once it completes, the SDK must be installed to a specific directory; it cannot be moved because it contains absolute paths. The installation script is generated by the build process and can be found here:
```
./build/tmp/deploy/sdk/maxiv-glibc-x86_64-meta-edf-app-sdk-cortexa72-cortexa53-amd-cortexa53-common-toolchain-v2025.2.sh
```
When you run this shell script, it asks you for the installation directory; in our case use this:
```
<base dir>/sdk-linux
```
Note that the SDK is for A53/linux only; the libraries necessary to cross compile applications for baremetal R5 are generated by Vitis in the "platform".


<!-- TOC --><a name="setup-vitis"></a>
## Setup Vitis
To cross compile applications for A53/linux and R5/baremetal it is possible to follow to ways:
- Vitis environment
- standard workflow from command line with the provided makefiles
As editor it's convenient to use visual studio code in both cases.
Vitis debugger is a useful tool, as it can download, run and debug (with step execution, breakpoints and all that) the applications for both processors.

In Vitis these items need to be setup:
- a platform for ZCU102 with the custom PL design made in Vivado
- an R5/baremetal app = control loop
- an A53/linux app = SCPI server

> [!NOTE]
>
> Even if makefile workflow is preferred, Vitis must be used once to generate the platform, which provides the libraries necessary to build R5 baremetal applications; for A53 linux, the libraries were compiled by yocto into the SDK, as outlined in previous section.

Start making a directory called:
```
<base dir>/vitis-workspace
```
cd there, run: ```vitis&``` and choose the previous directory as workspace. Click OK if it complains about "file watch errors": it's not a real problem.

First, we need to make a new "platform"; copy the `.xsa` from `vivado-prj` dir to `vitis-workspace` dir, so they are separated and one can work on vivado while using an old, stable xsa for vitis. Then use the menu command:
```
file/new component/platform
```
Start adding a R5#0/baremetal domain; add to it `libmetal` and `openamp`. 
In the R5 BSP, assign UART1 as stdin/stout, instead of the default UART0.
Regenerate the BSP

Then add an A53/linux domain.

Now it's time to compile the platform.

Then create R5app and A53app starting from the "empty application" example: select menu command:
```
File/New Example
```
Then go to the list that appears in the left pane and select `Empty Application` for R5 and `Linux Empty Application` for A53. Cal the R5/baremetal application `R5app` and the A53/linux one `A53app`.

> [!NOTE]
>
> If one starts from a new application using menu command `File/New Component/Application` instead of starting from an example empty application, important environment configuration are missed and the application won't compile.

For the A53 select the sysroot previously generated by yocto:
```
<base dir>/sdk-linux/sysroots/cortexa72-cortexa53-xilinx-linux
```

> [!TIP]
>
> Now, before proceeding, it's useful to make a backup copy of `<base dir>/vitis-workspace/_ide/.peers.ini`, in case it gets corrupted by a vitis crash; one can call it `.peers.ini.backup`.


Start with no source files (delete the sample .c and .h generated by vitis, if any); then close vitis, open a terminal and make a link in vitis `src` directory to the appropriate subfolders of the git-mirrored directory:
```
cd <base dir>/vitis-workspace/R5app/src
ln -s ../../../gitcode/r5ctrlr/c/r5 r5src
ln -s ../../../gitcode/r5ctrlr/c/common commonsrc

cd <base dir>/vitis-workspace/A53app/src
ln -s ../../../gitcode/r5ctrlr/c/a53 a53src
ln -s ../../../gitcode/r5ctrlr/c/common commonsrc
```

Then open Vitis again.

In r5app, open `settings/UserConfig.cmake` and:
- add the math library (`-lm` compiler directive)
- tell the compiler where to find the linker file, which is in the git-mirrored directory structure (it's file `<base dir>/gitcode/c/r5/lscript.ld`)
- add the git-mirrored directories as include directories (`-I` directive)
- add the sources to be compiled:
  ```
  commonsrc/rsc_table.c
  commonsrc/rproc.c
  commonsrc/platform.c
  commonsrc/sample_shmem.c
  r5src/r5_main.c
  r5src/cn0585_gpio.c
  r5src/cn0585_dac.c
  r5src/cn0585_adc.c
  r5src/doubledsplib.c
  r5src/sofiaio_spi.c
  ```
- `-O0`
- `-g3`


In A53/linux app, open `settings/UserConfig.cmake` and:
- add `-lm -lmetal -lopen_amp` linker directives
- add the git-mirrored directories (A53 and common) as include directories (`-I` directive); in the GUI you can put "src/a53src" and "src/commonsrc", as the "browse" link ends up putting an unnecessary absolute path
- add the sources to be compiled:
  ```
  src/commonsrc/rsc_table.c
  src/commonsrc/rproc.c
  src/commonsrc/platform.c
  src/commonsrc/sample_shmem.c
  src/a53src/linux_main.c
  src/a53src/SCPIserver.c
  ```
- `-O0`
- `-g3`

After compilation, the elf executables must be copied to the yocto structure to be included in the image; the locations are:
```
<base dir>/yocto-prj/sources/meta-user/recipes-apps/r5ctrlr-r5app/files/R5app.elf
<base dir>/yocto-prj/sources/meta-user/recipes-apps/r5ctrlr-scpi-serv/files/r5ctrlr-scpi-serv
```
Note that the A53 app has been renamed to `r5ctrlr-scpi-serv` (without the .elf extension); it is automatically run by linux at boot. The R5 executable is also automatically run at boot by u-boot.


<!-- TOC --><a name="compilation-without-vitis"></a>
### Compilation without vitis
It is possible to compile both the SCPI server for A53/linux and the control loop for R5/baremetal without Vitis: Makefiles are provided for this. Note that the makefile for linux automatically runs the environment setup (`. <base dir>/sdk-linux/environment-setup-cortexa72-cortexa53-amd-linux`) for the linux SDK previously compiled by yocto, so one does not need to do that manually.
Anyway, Vitis must be used at least once to build the "platform", i.e. the standard libraries for R5/baremetal; as said, the standard libraries for A53/linux are compiled by yocto.
